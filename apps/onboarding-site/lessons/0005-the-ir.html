Atlas Console · Lesson 5 · 3 min

Create Workflow

Describe the integration you want. Atlas drafts it using approved API actions.

Start with a request

Create Workflow opens on a quiet compose surface: a name, a plain-language prompt, and Draft. There is no scrolling capability ticker. Mention an authorized API action in the prompt and Atlas highlights it so you can open its details. Atlas may return a draft, ask a question, explain that an API action is missing, or ask for manual review. It should not guess when information is missing.

Answer questions in ordinary English

After Draft, Atlas continues as a short conversation when a detail is missing. It asks a question in ordinary sentences and names the step or API action when that is already known. Choose a suggested answer or write your own. Atlas does not guess the missing detail; your answer is checked the same way as the original request. If the request cannot be created, Atlas explains that in a sentence instead of inventing a draft. An Operator sees that they must switch to Author or Admin to create a workflow.

Review the draft

After a draft validates, a graph of that draft stacks underneath the prompt. Until then, Create Workflow stays a conversation without a graph, including questions and blocked outcomes. The graph shows steps, order, data mappings, credentials, and irreversible boundaries in ordinary language. Mappings you asked for look different from mappings Atlas inferred: amount and currency from the payment record look requested, while an unstated binding such as an idempotency key from the payment id looks inferred. Every inferred required field uses the same marking. It replaces the earlier list-style diagram, so the same draft is not shown twice.

YAML, follow-up, checks, and approval stay below the graph. Select a step to check:

  • which API action it uses;
  • how data moves into and out of it;
  • when it runs;
  • how long it may take and when it may retry; and
  • which credential it needs.

You can still open the .atlas.yaml authoring source to review or edit it. The Worker never executes that YAML directly. Saving an edit creates a new workflow version and checks it again.

Compile the source

Show source is for inspection and edits, not the primary review. The Backend resolves each capability name to an exact capabilityVersionId, orders dependencies, compiles mappings into a bounded transformation language, and recomputes the workflow fingerprint.

Missing or ambiguous mappings produce diagnostics or a question instead of invented glue code. Your answer is checked through the same compiler as hand-edited YAML.

Edit and check

Clicking Draft also runs checks once a draft exists, as the last step in the same drafting progress. Atlas does not ask for a second Run checks click on that path. If checks fail, Atlas repairs the draft once from that contract problem and runs checks again. If they still fail, the chat names the exact error, why it happened, and a suggested fix you can accept, the same way you accept a suggested answer. The graph stays visible and marks the failed step. Passing checks leave the graph in place and say this version is ready to approve, without listing individual checks. Approval stays Admin-only until checks pass.

Saving from Show source creates a new version and checks it again. A workflow with errors cannot be approved. The compiled plan is closed data interpreted later by Atlas; it is not generated JavaScript or TypeScript.

AI has a limited role

The model suggests a draft. The Backend checks it, and a person decides whether it should run. The model cannot see credentials or run the workflow.
