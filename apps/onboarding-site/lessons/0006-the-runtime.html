Workflow Catalog and approval

Find a saved workflow in the selected environment, then run checks and approve that version in ordinary language.

Find a saved workflow

Workflow Catalog is for browsing; Create Workflow is where you write, review, and approve a version. The Catalog shows one row per stable workflow, including its active version, latest version and status, last run, and updated time.

Search by workflow name or ID, filter by lifecycle status, sort by updated time, or move through pages of results. Changing the environment replaces the complete result set. Each row links by stable workflow identity, not a version ID.

Inspect one workflow

Open a Catalog row to see that workflow in the selected environment. The detail overview separates the active version used by new runs from the latest saved version, which may still be a draft or awaiting approval. Version history lists immutable versions, lifecycle state, approval evidence, and which version is active. Recent runs show their trigger, state, start time, duration and outcome when present, and link into the existing Runs timeline.

If an active version exists, the detail page shows an Invoke via API panel with the ingest gateway URL, the request body shape, the required payload fields from that version’s input schema, and a sample POST /ingest request for the selected environment’s local gateway (Development on port 4300, Production on 4301). Copy that request and send it to start the workflow. If none exists, the panel explains that the workflow cannot be invoked until a version is approved and active. The Catalog list has no Run control. Editing, checks, and approval stay in Create Workflow; the detail page links there instead of duplicating those controls. Switching environments clears the prior workflow detail and run history before loading the new scope.

Run the checks

On Create Workflow, Draft runs checks automatically once a draft exists, as the last step in the same drafting progress. An Author or Admin who can Draft can trigger those checks that way; Atlas does not ask for a second Run checks click on that path. Atlas does not show a list of individual tests. A passing run says this version is ready to approve. If a check fails, Atlas repairs the draft once from that contract problem and runs checks again. If they still fail, the chat explains the exact error, why it happened, and a suggested fix, and the graph marks the failed step.

Results belong to one workflow version. If you edit the workflow or change an API action, Draft again so checks run on the new version.

Keep runtime fixtures intentional

Each sandbox check replaces its selected mock-provider resources with the test-data profile so the runtime sees a repeatable starting point. Ordinary pnpm infra:up is different: it merges named mock-provider fixtures and leaves hand-seeded resources in place. pnpm infra:test:e2e uses the checked-in capability fixtures, while pnpm prepare-demo recreates Atlas with an empty capability catalog.

Execute approved API actions

The customer Worker does not contain a switch for named Payment, Billing, or Operations actions. Its Temporal activities load the approved capability fragment from Atlas, then map step input into the fragment’s path, query, header, and request-body fields. Required values are checked before the provider request. The workflow remains deterministic because HTTP calls happen only inside activities.

Before sending a request for a new run, the Worker requires the selected hostname to be an allowed host for the capability and to appear in the signed execution grant. A run admitted before grants carried allowed hosts may finish only against the Worker’s fixed local provider while that provider remains allowed; it cannot acquire a newly allowed remote host. Redirects are not followed. A JSON provider error keeps its declared error.type, so the interpreter can apply the approved retry or landing rule. Slack and HubSpot keep narrow explicit connectors only in official-test modes, where worker-held credentials are required; local rehearsal uses the generic binding.

Approve and activate

An Admin selects Approve this version only after checks pass. The button stays blocked until then, with a short reason such as switching to Admin, saving YAML changes, or fixing a failed check. Atlas packages the plan, required schemas, sandbox evidence, provenance, and approval binding into a canonical UTF-8 JSON document with the .atlas suffix, then signs it. It contains data for the interpreter, not generated workflow code.

Activation makes that signed bundle the version used by new runs.

Activation can be blocked when the Worker is offline or missing a required credential, host rule, or supported workflow version. The page shows the reason.

Compare or roll back

The version list shows who approved each version and when. Compare versions to see changed steps. Rolling back selects an older approved version for future runs; it does not change runs that already started.

One simple rule

New runs use the active signed bundle. Existing runs keep the immutable plan and capability pins they started with.
