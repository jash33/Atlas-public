Atlas Console · Lesson 7 · 3 min

Runs

Use Runs to follow workflow progress and handle failures after a start through the ingest gateway.

How a run starts

The Console does not start workflows. External systems and local demos post to the environment’s ingest gateway (POST /ingest on Development port 4300 or Production port 4301) with the workflow’s exact name and a plaintext payload. A webhook or schedule can also start a run. Before Temporal starts, the Worker verifies the bundle signature, tenant, environment, workflow and artifact IDs, irHash, capability pins, approval, activation, and ExecutionGrant. Each accepted run is bound to the workflow version that was active when it began.

The Catalog detail page shows a copyable sample request. Common demo payment IDs include:

  • payment_demo_001 completes normally.
  • payment_retry_demo_001 fails twice, retries, then succeeds.
  • payment_repair_demo_001 stops and waits for an operator.

See what happened

The Runs list shows each run’s duration, how many step retries happened, and whether the execution succeeded or failed once it stops. Select a run to see those same fields in the header, then inspect each step, how long it took, what failed, and whether Atlas retried it. Catalog recent runs also show duration and outcome when the worker has reported them. Sensitive values are hidden. Completed actions are listed so you can tell what should not run again.

A modified, revoked, inactive, or misplaced bundle fails before a provider call. Atlas records a sanitized verification event without storing bundle secrets or business payloads.

Handle a failed run

Atlas may let an Operator or Admin retry a step, continue the run, or abandon it with a reason. It only shows options that are safe for that run.

Continuing uses the saved history, so completed steps are not repeated. You cannot skip steps, edit the input, or switch workflow versions during a run.
