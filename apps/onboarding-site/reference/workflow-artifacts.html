Atlas · Reference

From request to executable artifact

Atlas compiles editable YAML into signed data. It never generates workflow source code.

natural-language request
  → reviewable .atlas.yaml
  → deterministic compiler and validator
  → typed CompiledWorkflowVersion
  → sandbox evidence and Admin approval
  → signed .atlas JSON bundle
  → customer Worker verification
  → generic Temporal interpreter

The representations

Executable means interpreted

The .atlas bundle is executable in the same sense that a database migration or declarative build plan is executable: a controlled runtime interprets its data. The bundle contains no JavaScript, TypeScript, WASM, shell commands, templates, or generated program.

Where the glue goes

Cross-API mappings live in a bounded transformation language inside the workflow IR. It can project and rename fields, build objects and arrays, use conditionals, and apply approved operations such as uppercase, concatenation, multiplication, or division.

Atlas resolves every input and output against pinned API schemas before approval. Missing fields, unsafe coercions, classification leaks, and unsupported operators stop the workflow. At runtime, the customer-side interpreter evaluates the same approved mapping before scheduling the destination capability.

What happens when a request is vague

The planner separates resolved mappings, validated candidates, and questions that need a person. Suggested answers come only from the authorized planner projection. A selected answer passes through the same deterministic compiler and validator as hand-edited YAML.

What the Worker verifies

Before Temporal starts, the Worker checks the bundle signature and digest, tenant and environment, workflow and artifact IDs, irHash, capability pins, approval, activation, and ExecutionGrant. A changed byte, unknown key, revoked version, or mismatched environment fails before a provider call.
