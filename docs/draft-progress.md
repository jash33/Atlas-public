# Draft progress

The Console creates a request with `PUT /v1/draft-requests/:requestId` and reads it with `GET` at the same address. Repeating the PUT with the same ID and body returns the existing request. A different body cannot reuse the ID. GET and DELETE include `organizationId` and `environmentId` in the query. All three operations require planning authorization and the same actor and scope that created the request.

Migration `074_draft_requests.cjs` stores the current stage and final result in PostgreSQL. Stages are `understanding`, `building`, `validating`, and `repairing`; the planner reports each immediately before that activity. Request status is `running`, `completed`, `failed`, or `cancelled`. A completed request can contain a validated draft, a clarification question, or another planning outcome. Elapsed time never advances a stage or completes a request.

The Console keeps the request address and editor context in session storage for refresh recovery. Reconnecting polls that request; it does not start another draft. Recovering a completed result does not rerun automatic checks or repairs. Connection failures leave the result unknown and retry the same request. Existing automatic test execution remains separate from backend drafting progress, pending #246; the Console reports it only while those checks run.

DELETE records cancellation before acknowledging it. The planner checks cancellation between stages, and the current Responses adapter passes the abort signal to fetch. Another backend process observes cancellation within its five-second heartbeat. Database updates prevent cancelled requests from accepting late results. The Console also records pending cancellation locally so a refresh cannot save a result the user already asked to discard.

Backend processes renew a heartbeat every five seconds. If a process stops renewing it for two minutes, reading the request records an interrupted failure. It never restarts model work automatically. Request records currently remain in the database until explicitly removed by an operator; a general retention policy is separate work.

Draft requests capture planning traces in their existing PostgreSQL state, including prompts, model settings, attempts, provider response metadata and usage, output, validation diagnostics, and repair decisions. The Responses adapter requests streaming while a draft log is active; other callers keep their existing response mode. Reasoning models in the GPT-5-and-later and o3-and-later families also request `reasoning.summary: auto`. Only summaries returned by the provider are shown; private reasoning and encrypted reasoning payloads are omitted. Connections that return ordinary JSON still record their response and final output.

The Model traces sidebar shows provider reasoning summaries as they arrive, with copy and JSON download actions for the complete saved log. Bold summary headings become collapsible sections connected by a vertical thread line. Sections start expanded and keep the user's collapse choice while text streams. The current section shows a spinner until the next heading, summary completion, or end of the model call; failed and cancelled requests stop all section spinners. It stays visible when drafting finishes or fails. Failed drafts hide the progress panel and its steps, while the sidebar retains the error and saved summaries. During drafting, short activity labels show Thinking, Working, or Checking draft alongside the reported focus. On smaller screens the sidebar stacks below the editor. Provider events are batched into database writes every 250 ms; the Console reads saved updates every second. A completed response is required before partial output can become a draft. Failure preserves the output received so far, including provider failure and incomplete-response events. Existing request ownership checks also protect these logs, and refresh recovery reads the same saved request.

Each request log has a 4 MB limit and records a visible truncation event when it reaches that limit. Logs omit transport body duplicates, authorization fields, common credential fields, and error stacks. Prompts and outputs can still contain user-provided business data. Logs follow the existing draft-request retention policy. The download includes the saved log and final result when available; it does not require provider-side response storage. Cancellation or server interruption retains events already written to the database.

Provider event format and summary settings follow the official [streaming guide](https://developers.openai.com/api/docs/guides/streaming-responses) and [reasoning guide](https://developers.openai.com/api/docs/guides/reasoning).

The sidebar also shows a live draft preview from streamed model output. It reads complete JSON fields before the response finishes: the intent summary, required inputs, proposed steps, and argument mappings. Partial strings are withheld, each new repair or retry replaces the earlier proposal, and previews remain separate from validated workflow state. The preview is labelled Still drafting while the request runs and Incomplete draft after failure or cancellation. It does not make an additional model call.
